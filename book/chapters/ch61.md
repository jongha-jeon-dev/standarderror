# An Alarm on the Inputs Cannot See the Outcome

Once a model is in production, the most common question about it is whether it is still working, and the most common answer is to watch its inputs. Labels arrive late or never; inputs arrive with every prediction. So a monitoring system compares each new batch of inputs with the training data, feature by feature, and raises an alarm when they differ. The practice rests on one sentence: *a drift alarm on a model's inputs tells you when the model has stopped working.* If it is false, teams are paged about models that are fine and left in silence while a model fails.

Part XIII starts where the earlier parts ended, at deployment, with the questions a practitioner meets afterwards: is the model still working, how sure are its numbers, is it fair, how often should it be retrained, and do the book's simulated findings hold on real data. This chapter takes the first. It trains a model in a simulated world, changes the world on purpose, and compares what an input alarm reports with what happened to the model. It then checks two other label-free monitors and a real shift.

## The experiment: a simulated world and an input alarm

### Three ways a deployed world can change

Write the joint distribution of inputs $x$ and outcome $y$ as $p(x, y) = p(x)\,p(y \mid x)$. A classifier learns $p(y \mid x)$, the relation between inputs and outcome, and the world can change in three standard ways.

- **Covariate shift**: $p(x)$ changes and $p(y \mid x)$ does not.
- **Concept drift**: $p(y \mid x)$ changes. Customers change their behaviour, a new fraud pattern appears, a treatment protocol changes. Gama and colleagues' survey of concept drift calls this *real drift*.
- **Label shift**: the prevalence $p(y)$ changes while each class looks as it did, so $p(x \mid y)$ is fixed. A disease becoming more common is the usual example.

Chapter 29 found that covariate shift costs little when the model is correctly specified, its functional form matching the true $p(y \mid x)$. This chapter tests the alarm rather than the model.

### The setup

The simulated world has five standard Gaussian inputs and a logistic outcome with coefficients (1.5, -1, 0.8, 0, 0) and intercept -0.3. A logistic model is trained on 5,000 rows drawn from it. The world is then changed, and the model is deployed on 50 batches of 200 rows and 50 batches of 2,000 rows for each scenario.

For each input the alarm runs a *two-sample Kolmogorov-Smirnov test*, which compares two samples of a single variable through their empirical cumulative distribution functions $\hat F_{\text{train}}$ and $\hat F_{\text{batch}}$. Its statistic is the largest vertical gap between them,

$$
D = \sup_x \left|\hat F_{\text{train}}(x) - \hat F_{\text{batch}}(x)\right|,
$$

and its p-value is the probability of a gap at least that large if both samples came from the same distribution. It detects any kind of difference, in location, spread or shape. The alarm fires if any of the five p-values falls below 0.05 divided by five, a *Bonferroni correction* discussed below.

The code shows one batch of 2,000 rows under two changes, the first input's mean moved by one standard deviation (`shift`) and its coefficient reversed (`flip`), printing the smallest of the five p-values and the accuracy.

```python
import numpy as np
from scipy.stats import ks_2samp
from sklearn.linear_model import LogisticRegression
from standarderror.ml import deploy

rng = np.random.default_rng(0)
X, y = deploy.drift_world(5000, rng)          # the world at training time
model = LogisticRegression().fit(X, y)
for kw in ({"shift": 1.0}, {"flip": 1.0}):    # inputs move; relation turns
    Xb, yb = deploy.drift_world(2000, rng, **kw)
    p = min(ks_2samp(X[:, j], Xb[:, j]).pvalue for j in range(5))
    acc = np.mean(model.predict(Xb) == yb)
    print(f"{kw}: smallest input p-value {p:.1e}, accuracy {acc:.3f}")
```

```text
{'shift': 1.0}: smallest input p-value 2.7e-199, accuracy 0.806
{'flip': 1.0}: smallest input p-value 8.9e-02, accuracy 0.466
```

The two lines contain the chapter's result: the test was certain when the inputs moved and the model improved, and saw nothing when the relation reversed and the model was wrong on more than half the rows.

## Input alarms fire when nothing is wrong

### A large shift that improves the model

Move the first input's mean by one standard deviation and leave $p(y \mid x)$ unchanged: pure covariate shift. The alarm fired on every batch, of either size. Accuracy *rose*, from 0.771 on the validation rows before deployment to 0.801.

The reason is presumably geometric. The moved input carries the largest coefficient, so moving it carries more of the new rows far from the decision boundary, the surface where the model's predicted probability is one half. There the model is surer and right more often. A team paged by this alarm would find a model doing better than ever.

### A small shift that a large batch makes significant

Move the same input by a tenth of a standard deviation instead. On batches of 2,000 the alarm fired on 74% of them; on batches of 200, on 14%. Accuracy did not change measurably: 0.776 against 0.778 with no drift.

This is ordinary significance testing. The statistic's sampling noise shrinks as the samples grow, so a fixed true difference gives ever smaller p-values, and a large enough batch makes any difference significant. Whether the difference matters is a separate question the test does not ask, and the same shift fires the alarm more often in a busy week than a quiet one.

### Many inputs, many chances to fire

The last way to raise alarms over nothing is to watch many inputs. If each of $m$ inputs is tested at level $\alpha$ and nothing has changed, the chance that at least one fires, the *family-wise error rate*, grows with $m$; for independent tests it is $1 - (1 - \alpha)^m$.

With no drift at all and each input tested at 5%, at least one test fired in 23% of batches with 5 inputs, 63% with 20 and 99% with 100. Run weekly, a 20-input monitor would fire about 33 times a year with nothing wrong.

The Bonferroni correction tests each input at $\alpha / m$, which bounds the family-wise error rate at $\alpha$ whatever the dependence between tests. Here it brought the rate back near the 5% it promises, between 2.0% and 7.5% over 200 batches, at the price of missing small real shifts.

## Input alarms are silent when everything is wrong

### Changing the relation, not the inputs

Now leave the inputs alone and change $p(y \mid x)$: the first input's coefficient moves from +1.5 to 0 (half-reversed) or to -1.5 (reversed). This is concept drift. The input alarm fired on 0% and 2% of batches, no more than with no drift at all. Accuracy fell to **0.633** and **0.466**, below a coin flip in the second case.

The silence is not a weakness of this test. The inputs came from exactly the training distribution, so any test of $p(x)$, however powerful, is testing a true null hypothesis and fires at its false-alarm rate.

### Two label-free monitors with the same blind spot

Two more label-free monitors were equally blind. The first, the same test applied to the model's predicted probabilities, fired on 2% of batches: the scores are a function of the inputs, and the inputs had not moved.

The second is an estimate of accuracy built from the unlabelled batch by *importance weighting*, the method of Sugiyama and colleagues. Under covariate shift, the accuracy on the new data can be estimated from labelled validation rows by weighting each one by the *density ratio*

$$
w(x) = \frac{p_{\text{new}}(x)}{p_{\text{train}}(x)},
$$

estimated here with a logistic *domain classifier* trained to tell validation rows from deployment rows (its predicted odds are, up to a constant, the ratio). The estimate was within 0.002 of the truth when the inputs moved, because covariate shift is exactly its assumption: it reweights the inputs and keeps the old $p(y \mid x)$. Under concept drift it said 0.771 throughout. It reported the past.

### Why nothing label-free can detect concept drift

The three monitors use nothing from the deployment batch but its inputs (the accuracy estimate's labels are the old validation labels). A change in $p(y \mid x)$ with $p(x)$ fixed leaves the distribution of every such quantity unchanged, so nothing computed without outcomes can tell the drifted world from the original. The only signal is in labelled outcomes; Chapter 64 measures what it costs when they arrive late. The table below lists every scenario.

## Label shift and a real shift

### Label shift: accuracy hides what the probabilities show

Between the two sits label shift. Moving the prevalence from 0.46 to 0.20 changes the mix of the two classes' inputs, and the input alarm fired on every batch. Accuracy stayed close (0.794 against 0.771). The probabilities did not: the model's average predicted probability was 0.363 against an actual rate of 0.201. At a prevalence of 0.8 it was 0.596 against 0.803.

By Bayes' rule, $p(y \mid x)$ depends on the prior $p(y)$, so it moves with the prevalence while the model keeps the old one, and a decision at a fixed probability threshold would be wrong in proportion. Lipton, Wang and Smola showed how to estimate the new prevalence from unlabelled predictions under exactly this assumption.

### A real covariate shift on breast cancer

The Wisconsin diagnostic breast cancer data give a real version of the first scenario. A standardised logistic model trained on 300 random tumours scored 0.967 on the other 269, with no feature alarmed. Deployed only on tumours above the training median of mean radius, nineteen of the 30 features raised an alarm, the share of malignant tumours rose from 38% to 70%, and accuracy was 0.941, 8 errors in 135 tumours. On the largest quarter of tumours, 20 features raised an alarm and accuracy was 0.969.

Differences of that size are within what so few tumours can measure, given the binomial error bar of Chapter 1. A monitor would have reported a crisis that the outcomes did not show. The next chapter turns from whether a model is working to how sure its numbers are.

## In practice

- **Treat an input alarm as a reason to look, not as evidence of harm.** Before escalating, check labelled performance; a moved input can leave accuracy unchanged or improve it.
- **Do not read silence as health.** Input alarms, score alarms and importance-weighted accuracy estimates cannot detect a change in $p(y \mid x)$.
- **Budget for labelled outcomes**, however few and late: a regular labelled sample, or delayed outcomes joined back to predictions. A change in the relation shows up nowhere else.
- **Correct for the number of features watched** (test each at $\alpha / m$, accepting that small real shifts will be missed), and **fix the batch size or alarm on effect size**, since on large batches a p-value alarm fires on shifts too small to matter.
- **Compare mean predicted probability with the observed rate** whenever outcomes arrive; under label shift, accuracy can hold while the probabilities are wrong.

## Limits of the evidence

- **Five inputs, one model.** Real monitors watch hundreds of features and use other tests, such as population stability indices and embedding distances. Their behaviour with sample size and with many features is the same in kind as the Kolmogorov-Smirnov test's.
- **Shifts chosen to separate the cases.** Real drift usually mixes a moving input distribution with a changing relation, and an input alarm will then often fire for the wrong reason at the right time. That coincidence is not a mechanism to rely on.
- **A correctly specified model.** Chapter 29 showed that a misspecified model does lose accuracy under covariate shift, so an input alarm is more informative for such a model. It still cannot see a change in the relation.
- **Labels assumed absent.** Where labels arrive quickly, monitoring the outcome directly makes most of this unnecessary.

## Key points

1. An input alarm fired on every batch when an input moved a standard deviation, and accuracy rose from 0.771 to 0.801.
2. When the relation between inputs and outcome reversed and the inputs stayed put, input and score alarms fired no more than with no drift, a label-free accuracy estimate said 0.77, and accuracy was 0.47.
3. With 20 inputs tested separately, 63% of batches raised an alarm with nothing wrong; with large batches, a shift too small to matter raised it 74% of the time.
4. Treat input drift as a reason to look, not as evidence of harm. Budget for labelled outcomes, however few and late, because a change in the relation shows up nowhere else.
